# Checklist final do projeto

## Relação entre TCC e escopo de IHC

- [ ] Está claro qual é o **tema/contribuição do TCC** e qual é o **escopo de IHC da disciplina**.
- [ ] A equipe registrou se o TCC já previa interface, previa parcialmente ou não previa.
- [ ] Se o TCC não previa interface, a equipe explicou como derivou o recorte de IHC a partir da contribuição técnica.
- [ ] O usuário escolhido para IHC é plausível e possui relação clara com o valor produzido pelo tema do TCC.
- [ ] O objetivo do usuário é descrito como resultado no mundo real, e não como “usar o sistema”.
- [ ] A interface da disciplina não é apresentada como obrigação formal do TCC, salvo se isso tiver sido acordado com o orientador.
- [ ] O recorte de IHC é pequeno o suficiente para ser modelado, prototipado e avaliado durante a disciplina.
- [ ] O projeto consegue explicar a cadeia **problema humano → contribuição computacional → forma de uso → impacto potencial**.

## Estrutura e apresentação

- [ ] O README explica problema, público, contexto, contribuição do TCC e recorte de IHC.
- [ ] Todos os 14 arquivos de entrega estão linkados e abrem corretamente.
- [ ] Não existem links locais quebrados.
- [ ] Imagens e diagramas são legíveis no GitHub.
- [ ] Arquivos editáveis dos principais diagramas foram preservados quando possível.
- [ ] Entregas individuais identificam o autor.
- [ ] As quantidades mínimas por integrante foram atendidas.
- [ ] Links externos (Figma, Forms, vídeos) foram testados sem autenticação privilegiada.

## Coerência de IHC

- [ ] Público-alvo, personas e participantes de pesquisa/teste são coerentes com o escopo de IHC.
- [ ] Cenários de problema descrevem o problema/atividade sem antecipar a solução.
- [ ] Tarefas analisadas correspondem a objetivos importantes das personas.
- [ ] Modelo conceitual, signos e MoLIC usam terminologia consistente.
- [ ] MoLIC contém caminhos principais, alternativas e rupturas relevantes.
- [ ] O Figma cobre os fluxos modelados e não cria funcionalidades críticas sem rastreabilidade.
- [ ] Metas de usabilidade são verificáveis.
- [ ] Em projetos técnicos, resultados do algoritmo/modelo foram traduzidos para linguagem e decisões compreensíveis ao perfil de usuário escolhido.

## Justificativa das telas e padrões

- [ ] Cada tela importante possui relação com uma tarefa/objetivo rastreável.
- [ ] Dashboard, se existente, apoia uma decisão ou necessidade de acompanhamento concreta.
- [ ] Relatórios apresentam informação necessária para uma tarefa, e não apenas “números porque existem”.
- [ ] Histórico, busca, ordenação e filtros possuem volume/uso que justifique sua existência.
- [ ] Telas administrativas existem porque há atividades reais de configuração, governança ou operação.
- [ ] CRUDs representam entidades e tarefas relevantes; não foram criados apenas para aumentar o número de telas.
- [ ] Gestão de usuários/perfis/permissões, se existente, considera papéis, prevenção de erros e consequências de alterações.
- [ ] Telas de configuração não expõem complexidade técnica desnecessária sem justificativa.
- [ ] Estados de carregamento, processamento, vazio, erro, sucesso e recuperação foram considerados quando pertinentes.
- [ ] Comparações e visualizações ajudam o usuário a interpretar diferenças e tomar decisões.

## Avaliação

- [ ] Cada avaliador heurístico percorreu todas as telas/estados relevantes.
- [ ] As 10 heurísticas foram explicitamente verificadas por cada avaliador.
- [ ] Violações têm evidência, localização, severidade justificada e recomendação.
- [ ] Problemas duplicados entre avaliadores foram consolidados sem apagar a autoria da descoberta.
- [ ] O número final de usuários observados atende ao exigido pela disciplina.
- [ ] Participantes finais representam o público-alvo e não são membros da equipe.
- [ ] Se o perfil profissional é difícil de recrutar, qualquer uso de participante aproximado/proxy foi justificado e registrado como limitação.
- [ ] Tarefas de teste possuem cenário, instrução neutra e critério de sucesso.
- [ ] Tempos, erros, ajudas, sucesso e satisfação foram registrados por usuário/tarefa.
- [ ] A avaliação mede a **interação com o protótipo**, e não tenta substituir a avaliação técnica/científica do algoritmo ou modelo do TCC.
- [ ] A conclusão identifica padrões, problemas prioritários e mudanças concretas.

## Ética e privacidade

- [ ] Há consentimento compatível com a atividade realizada.
- [ ] O participante sabe que pode interromper a participação.
- [ ] Dados pessoais desnecessários não foram coletados/publicados.
- [ ] Vídeos/áudios/imagens de participantes só são compartilhados com autorização.
- [ ] Resultados públicos usam IDs anônimos (`U01`, `U02`...).

## Comunicação e INOVA

- [ ] A equipe consegue explicar o projeto sem depender apenas de jargão técnico.
- [ ] O protótipo demonstra como uma pessoa poderia usar ou se beneficiar da contribuição técnica.
- [ ] A apresentação deixa claro o que é resultado real do TCC e o que é hipótese/protótipo da disciplina.
- [ ] O potencial de aplicação, mercado ou extensão é apresentado sem afirmar validações que ainda não ocorreram.
